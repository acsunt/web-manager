建议按这个顺序做

  • 先修 deleteCategoryModal / batchDeleteModal 的破损标签，确认删除流程能关、能点
  • 用显式 handler 对象替换 eval(name)，HTML 内联事件逐步改成 addEventListener
  • 渲染名称、路径、URL 时统一走 textContent 或转义，搜索和树选择优先
  • 自定义代码默认只允许 CSS；HTML/JS 需要单独开关，导入主题不要自动执行脚本
  • 主数据迁 IndexedDB；背景图和图标禁止以大 base64 写入 localStorage
  • 按域拆 main.js：tree / workspace / theme / io / tools，而不是再抽一层工具函数

分层说明

1. 可靠性：比新功能更值钱

这是个人数据工具。清空、删除、导入一旦出错，用户没有 git 可回滚。建议优先补这三件事：破坏性操作前自动导出一份备份、主数据保存失败要提示（现在只有主题配额提示）、导入 JSON 做结构校验而不是直接当树用。

localStorage 会先撑爆，再丢数据
背景图按 JPEG base64 写入主题配置，自定义图标也可能是 data URL。条目一多，保存会静默失败。中期应把 webManagerDataProMax 迁到 IndexedDB，图片只存 URL 或 Blob。

2. 安全：按「会导入别人的备份」来设计

即便主要是自用，导入/导出已经存在。现在有三条会放大风险的路径：自定义代码执行 script、名称走 innerHTML、用 eval 找函数名。最低成本改法是：自定义代码默认当 CSS；渲染一律转义；handler 写成一张明确的函数表。

3. 结构：按业务域拆，不要再抽空壳

保留

继续做静态页面，不要急着上 React。交互已经成型，重写成本会吞掉功能迭代。

值得拆

tree.js、workspace.js、theme.js、io.js、tools.js。每个文件对外只暴露 init / render / 少量 action。

先别做

不要再往 utils.js 堆零散函数，也不要上构建链，除非开始写测试或要打包离线资源。

4. 仓库卫生

旧/ 和 历史/ 里各有一份接近 300KB 的完整 HTML，和当前模块版功能重叠。建议移出工作区，或只在 git tag 里保留。同时补一份 README：怎么打开、数据存在哪、如何导出备份。标题版本号也应改成和 13.x 一致。

一句话结论

产品已经能用，而且功能密度很高。接下来不要加主题或工具，先把删除弹窗修好，再把数据和自定义代码从「会丢、会执行」改成「可备份、默认可信」。

依据：当前工作区源码。main.js 196KB，index.html 63KB，历史单文件约 285–293KB。
